# FPF Independent QA Controller

This repository is the trust root for FPF independent QA execution.

It is deliberately separate from any Candidate repository. Candidate code is
treated as untrusted input. The Controller owns the test specification, the
trusted test harness, the final evaluator, the signed QA result, and the
attestation verification step.

## Trust boundary

- Controller repository: `huangzuomin/fpf-qa-controller`
- Controller workflow: `.github/workflows/fpf-independent-qa.yml`
- Candidate repository: supplied as a dispatch input and restricted by the
  trusted workflow
- Candidate credentials: never mounted into the execution container
- Execution network: disabled
- Candidate source: read-only
- Harness and specification: read-only, supplied by this Controller
- Final verdict: generated by the Controller evaluator, never by Candidate

`mode=candidate` additionally runs the exact Candidate target unittest module
and the full unittest discovery suite inside the network-disabled container.
Their raw exit codes and executed counts are supporting evidence. The six
Controller-owned assertions remain the semantic gate and cannot be replaced by
Candidate-authored tests.

The current Controller maintainer is the repository owner. The FPF DEV and
Candidate execution identities do not receive write access to this repository.

## Synthetic acceptance

The workflow starts with `mode=synthetic`. This exercises the complete
workflow without running the FPF Candidate implementation:

1. bind the Controller repository, ref, commit, task, and Candidate SHA;
2. execute the Controller-owned test suite in a hardened container;
3. evaluate the raw evidence against the Controller-owned specification;
4. create a QA-specific predicate and sign the immutable QA bundle;
5. independently verify the Sigstore/GitHub attestation.

Only a completed run with a successful standalone attestation verification may
be cited as synthetic Controller acceptance evidence.

## GEO Core PR 293: blocked observation

`qa/geo293-spec.json` fixes the repository, PR, base, head and changed-file
set. Issue #292 is the source of the scope authorization; the exact file set
was independently taken from the PR diff at the pinned revisions and is
stored as path hashes (which do not protect against guessing). The
Controller-owned tests exercise its admission helpers with wrong SHAs, races,
extra files, forged evidence, identity collisions and failure results.

`.github/workflows/geo293-observation.yml` runs only from current Controller
main. It projects two PR snapshots to the fields needed for runner-local
admission and checks a read-only checkout in a network-disabled container.
No GEO observation artifacts are uploaded or signed: PR data, candidate
paths, source, logs, result and even projected fields remain runner-local.
The only intended public log line is the constant BLOCKED status. Publishing
evidence requires a separately reviewed public-data allowlist and an actual
enforced publication boundary; attestation verification is not implemented.
Configure the
Controller Actions secret `GEO_CANDIDATE_READ_TOKEN` with only the necessary
read access to GEO contents and pull requests. No governance App secret is used.

This is an observation prototype, not an approval chain: it always returns
`BLOCKED`. The identity and evidence helper tests are not live identity or
evidence verification, the PR snapshots precede the isolated observation,
and the Controller does not yet execute independent adversarial tests against
the candidate's review script. It does not validate candidate semantics or
human semantic review. Candidate-authored logs and tests are not independent
evidence. Signed provenance does not imply approval. No Review submission job
exists; implementing one requires independently established semantic rules,
identity separation, evidence authentication, fresh base/head checks and a
separately reviewed authorization design. The workflow is intentionally not
dispatchable from this branch as a trusted run.
